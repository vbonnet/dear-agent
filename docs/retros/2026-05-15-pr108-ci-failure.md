# DEAR Retro: PR #108 Was Red Before It Was Opened

**Date:** 2026-05-15
**Severity:** High (fourth CI retro; the merge gate the 5/10 retro
"closed" was bypassed by direct-to-main security pushes, leaving two
required checks red on `main` and poisoning every open PR)
**Status:** Code break fixed in this PR; two governance gaps escalated,
not silently patched

This is the fourth CI retro
([5/09](./2026-05-09-ci-red-streak.md),
[5/10 cascade](./2026-05-10-ci-cascade-cleanup.md),
[5/10 merge gate](./2026-05-10-ci-red-and-unguarded-merges.md)). The 5/10
merge-gate retro ended: *"The next CI red — if it happens — will be a PR
that doesn't merge, not a `main` that everyone builds on top of."* That
prediction was wrong within five days, and the reason it was wrong is the
whole point of this retro.

## Define

**The task:** PR #108 (`feat/handoff-confidence-rebased`, "handoff
confidence levels") is failing CI. Fix the failures, address legitimate
gemini-code-assist feedback, and explain in a retro how a PR that fails
CI got pushed.

**The framing was slightly wrong, and that matters.** "How did *we push
a PR* that fails CI" presumes the PR's own diff broke something. It did
not. PR #108 touches `agm/internal/gateway`, `pkg/acceptance`,
`pkg/vroom`, and docs — 13 files, zero of them under
`engram/internal/security`, `wayfinder/pkg/sandbox`, or `scripts/`. The
real question is: **why does an unrelated feature PR inherit a red CI it
had no hand in creating?**

**The invariant under test** (restated from the 5/10 retro): `main` is
green, and it stays green because *no change reaches `main` without its
required checks passing first*. Not "PRs are gated." `main`.

## Execute

`gh pr checks 108` — two failing required checks, eleven green:

| Check | Result | Caused by PR #108? |
|---|---|---|
| `Build & Test (ubuntu-latest)` | ❌ 7 sandbox tests | No |
| `Bash Script Size Check (20-line limit)` | ❌ 2 scripts | No |
| `Build & Test (macos-latest)` | ✅ | — |
| (9 others) | ✅ | — |

**Failure 1 — `Build & Test (ubuntu-latest)`.** Seven tests in
`engram/internal/plugin` and `engram/internal/security` fail, all with:

```
failed to apply sandbox: apparmor_parser failed to load profile
(failing closed; refusing unsandboxed exec): exit status 1
```

`macos-latest` passed because the macOS sandbox path is different code
(`sandbox_darwin`); the Linux path is the only one exercising AppArmor.
Root cause is in `engram/internal/security/sandbox_linux.go`
(`isPermissionDeniedError`): the fail-closed logic introduced by
`6afbf8ce59 security: fix CRITICAL + HIGH deepsec-scan findings` keeps the
validation-only fallback **only** when `apparmor_parser` exits with code
`13` or returns `os.ErrPermission`. On GitHub's `ubuntu-latest` runner an
unprivileged `apparmor_parser -r` exits with **status 1**, not 13. So the
benign "dev/CI has no CAP_MAC_ADMIN" path is misclassified as a real
profile failure, and every sandbox-backed test fails closed.

The fail-closed behavior is *correct security design* — a profile-text
injection that produces an unparseable AppArmor profile must not silently
drop the sandbox. The bug is that "can this environment load profiles at
all" was inferred from a single, distro-specific exit code.

Fix (this PR): replace the exit-code heuristic with a constant, known-good
**probe profile**. When a real profile fails to load, we attempt to load
`apparmorProbeProfile` (fixed source, never attacker-influenced). If even
*that* cannot load, the environment forbids policy loading entirely
(unprivileged dev/CI) → validation-only fallback, same intent as the old
exit-13 check but robust to exit code and stderr wording. If the probe
*can* load but the generated profile cannot, the difference is the
permission-derived profile text → still fail closed. The
privilege-escalation guarantee from `6afbf8ce59` is preserved; the
brittle exit-code dependency that broke CI is gone. Cross-compiled and
vetted for `GOOS=linux`; the platform-agnostic gateway suite is green.

**Failure 2 — `Bash Script Size Check (20-line limit)`.**
`scripts/deepsec-incremental.sh` (82 logical lines) and
`scripts/install-deepsec-hook.sh` (60) exceed the 20-line policy and have
no row in `.github/language-policy/exceptions.db`. Both files were
introduced whole by `9b7104d35d feat(security): incremental deepsec
scanning`. Neither is touched by PR #108.

The mechanical fix is one `INSERT` into the SQLite exceptions DB. **I did
not make it, deliberately.** An exceptions-DB row is a *formal policy
waiver* — `approver`, `reason`, `sunset_date`. Writing one in the user's
name, with a reason and sunset date I invented, to silence a gate on a
feature PR that has nothing to do with those scripts, is fabricating a
governance approval. The auto-mode classifier flagged exactly this, and
it was right to. A waiver for security tooling that breaches the bash
policy is a decision the repo owner makes explicitly; it is not a
side-effect of an unrelated feature merge. This is escalated, not
patched — see Retro.

**Gemini feedback** (two `medium` comments, both legitimate, both fixed
in `agm/internal/gateway/handoff_prompt.go`):

1. *Template duplication.* The `confidence`, `artifacts`, and
   `next_steps` `{{define}}` blocks were byte-identical across all three
   handoff templates — a drift hazard. Extracted into one
   `sharedHandoffDefines` constant concatenated onto each template body.
   Rendered output is unchanged (verified: the post-`---` tail was
   already identical across the three; tests assert via `strings.Contains`
   and pass).
2. *`%.2f` rounding across band boundaries.* Band floors are 0.40
   (MEDIUM) and 0.75 (HIGH). A MEDIUM score of `0.749` printed as `0.75`
   under `%.2f` — the inclusive HIGH floor — contradicting the
   `Level: MEDIUM` line. Changed to `%.3f`, matching the precision
   `handoff_confidence.go` already uses in its validation errors.

## Audit

How the two failures reached `main`, from the git and Actions record:

```
9b7104d35d  2026-05-15 07:31  feat(security): incremental deepsec scanning   → NO PR (direct push to main)
6afbf8ce59  2026-05-15 07:43  security: fix CRITICAL + HIGH deepsec findings  → NO PR (direct push to main)
654bf99b15  2026-05-15 17:04  Merge branch 'security-fixes-deepsec'           → NO PR (direct push to main)
2603b71fd7  2026-05-15 18:01  security: fix CRITICAL handlebars CVE           → NO PR (direct push to main)
```

`gh api .../commits/<sha>/pulls` returns empty for all four. They were
`git push origin main`, not merges of reviewed PRs.

- `9b7104d35d` introduced the two oversized bash scripts → **`Bash
  Script Size Check` red on `main` since 07:31**.
- `6afbf8ce59` introduced the exit-code-13 fail-closed bug → **`Build &
  Test (ubuntu-latest)` red on `main` since 07:43**.

Both are required status checks. Branch protection (`strict: true`) makes
every PR's base be up-to-date with `main` before merge — so a red `main`
is not a localized problem, it is a **broadcast**: every open PR's
required-check run includes the inherited breakage. PR #108 was red the
moment it rebased onto a red `main`, regardless of its own diff.

Why required status checks did not stop this: **they gate pull request
merges, not direct pushes.** A direct `push` to `main` is governed by
`enforce_admins`, which is `false`. The 5/10 retro set it `false`
*on purpose* and documented the trade-off:

> `enforce_admins` is left **off** intentionally — this is a solo-dev
> repo, and a self-locked admin can't recover from a busted required
> check. The trade-off is documented here so it's not silently
> re-enabled later without thought.

That trade-off was the exact hole used here. Four times in one day, under
"CRITICAL CVE / security fix" urgency, the protected path was bypassed by
the one actor protection doesn't bind. Security fixes are the *worst*
category to ship unreviewed and untested: `6afbf8ce59` was itself a
security hardening commit, and it shipped a CI-breaking regression with
zero CI and zero review.

Two further drifts, both predicted by the 5/10 retro's own open
follow-ups:

- **Required-checks list drifted.** The 5/10 retro required *7* checks
  including `Language Policy Enforcement`. Live protection now lists *6*;
  the `Language Policy Enforcement` umbrella context is gone (the
  job-level `Bash Script Size Check` survived, which is the only reason
  Failure 2 still blocks #108's *merge*). Follow-up #3 of that retro —
  "a small Go tool that diffs workflow job names against live
  protection" — was never built. Memory note
  `dear-agent-retro-followthrough.md` is the recurring pattern: a retro
  that proposes a mechanism but does not wire it will recur.
- **`required_pull_request_reviews`** is now `null` (5/10 set it to `0`).
  Minor, but it is unreviewed drift in the same rule.

## Retro — three gaps, one root

**Root:** the merge gate binds PRs and non-admins; it does not bind the
admin's direct pushes. "I'll only push to `main` when green" is the
same wish, in the same words, that the 5/09 retro already named as a wish
— just relocated from "merge" to "push," and triggered by security
urgency instead of feature velocity.

**Gap 1 — Direct-to-main pushes bypass every check (the load-bearing
one).** Wiring an enforcement mechanism *here* would mean bundling a
branch-protection/pre-push change into an unrelated feature PR — the
precise anti-pattern this retro is about. So this PR does **not** smuggle
it in. The mechanism is specified for a dedicated follow-up so it cannot
evaporate:

- Option A (recommended): a local pre-push hook (the deepsec hook infra
  from `9b7104d35d` already exists to extend) that refuses
  `push <remote> main` from the working clone and prints the
  worktree→PR runbook. Reversible, binds the actor, no plan upgrade.
- Option B: `enforce_admins: true` with a written break-glass procedure
  (`gh api ... -X PUT enforce_admins=false`, fix, re-enable). Closes the
  hole entirely; costs recovery friction. The 5/10 trade-off should be
  *re-decided in the open*, not left as the default that just failed.

**Gap 2 — The exceptions-DB waiver is the owner's call.** The bash-size
red is real and pre-existing on `main`. It should be resolved by an
explicit decision, recorded honestly:
- grant a waiver — owner runs the `INSERT` (or an `engram policy add`
  subcommand, which does not exist yet and is the cleaner fix: the CLI is
  read-only today, so the only way to add an exception is hand-written
  SQL, which is *why* fabrication was the path of least resistance), with
  a true reason and a real sunset; **or**
- split/refactor the two scripts under 20 logical lines (the Go-refactor
  the policy recommends).
Either way it is a standalone change on its own branch, not cargo on
#108. Until then, `main` and #108 stay red on this check — which is the
*honest* state and exactly the signal the gate exists to send.

**Gap 3 — Required-checks list has no drift detector.** Re-file the 5/10
retro's follow-up #3 as owned work: a CI job (or `engram policy`-style
tool) that fails when `.github/workflows/*.yml` job names and the live
`branches/main/protection` required-checks set disagree. A protection
rule no one verifies is the cosmetic branch protection the 5/10 retro
already wrote a retro about.

**Lesson.** Three CI retros said the merge pipeline trusted discipline
over enforcement, and shipped enforcement for the *merge* path. The path
that broke this time is the *push* path, by the *one actor* the
enforcement deliberately exempts, under the *one pressure* (security
urgency) most likely to justify the exemption to oneself in the moment. A
gate with a documented hole is a gate that will be walked through exactly
when it matters most. The fix for a feature PR inheriting red CI is not
to quietly launder `main`'s breakage through the feature PR — it is to
fix the code regression at its source (done here for the sandbox bug) and
escalate the governance decisions as governance decisions (done here for
the waiver and the protection hole).
