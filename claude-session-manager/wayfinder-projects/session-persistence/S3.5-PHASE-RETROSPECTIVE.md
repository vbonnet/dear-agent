## Design Decisions: Rationale & Trade-offs

### 1. Dynamic Status Computation

**Decision**: Status is computed from `lifecycle` + tmux state, never stored.

**Rationale**:
- Stored status goes stale when tmux crashes
- Computed status is always accurate
- Single source of truth (tmux)

**Trade-off**:
- Pro: Always correct
- Con: Requires tmux check on every `list` (acceptable, fast operation)

**Confidence**: ⭐⭐⭐⭐⭐ (unanimous approval from all reviewers)

### 2. File Locking with 60s Timeout

**Decision**: Locks timeout after 60s (stale threshold).

**Rationale**:
- Protect against crashed processes holding locks forever
- 60s is long enough for normal operations
- Short enough to recover quickly from crashes

**Trade-off**:
- Pro: Auto-recovery from crashes
- Con: Long operation (>60s) could lose lock (unlikely)

**Confidence**: ⭐⭐⭐⭐⭐ (60s is conservative, safe)

### 3. Atomic Operations (Temp + Rename)

**Decision**: All writes use temp file → rename pattern.

**Rationale**:
- POSIX guarantees atomic rename
- Crash during write doesn't corrupt original
- No partial states

**Trade-off**:
- Pro: Crash-safe
- Con: Extra file I/O (negligible cost)

**Confidence**: ⭐⭐⭐⭐⭐ (industry standard pattern)

### 4. Migration Auto-Triggers on Load

**Decision**: v1 → v2 migration happens automatically when loading v1 manifest.

**Rationale**:
- Transparent to user (no manual migration step)
- Happens on-demand (only when manifest is accessed)
- Backup created (.v1.bak) for safety

**Trade-off**:
- Pro: Seamless upgrade
- Con: First operation after upgrade is slower (one-time cost)

**Confidence**: ⭐⭐⭐⭐⭐ (standard database migration pattern)

### 5. Stream Processing for history.jsonl

**Decision**: Use bufio.Scanner with 10MB line buffer, skip malformed lines.

**Rationale**:
- history.jsonl can be 100MB+ (unbounded)
- Full file load would exhaust memory
- Streaming keeps memory bounded

**Trade-off**:
- Pro: Handles any file size
- Con: Slightly more complex code (acceptable)

**Confidence**: ⭐⭐⭐⭐⭐ (required for large files)

### 6. Doctor UUID Check Optimization

**Decision**: Parse history.jsonl once, cache all UUIDs in map, O(1) lookup.

**Rationale**:
- O(N²) approach: N sessions × read history N times = 50² = 2500 reads
- O(N) approach: 1 read + N map lookups = 51 operations
- 50× improvement

**Trade-off**:
- Pro: Massive performance gain
- Con: Memory for UUID map (negligible, ~50 UUIDs × 36 bytes)

**Confidence**: ⭐⭐⭐⭐⭐ (clear win, no downside)

### 7. TmuxInterface Abstraction

**Decision**: Define interface, use dependency injection for testing.

**Rationale**:
- Real tmux in production
- Mock tmux in tests (no tmux dependency for CI)
- Testable without external dependencies

**Trade-off**:
- Pro: Fast, reliable tests
- Con: Extra abstraction layer (minimal complexity)

**Confidence**: ⭐⭐⭐⭐⭐ (standard Go testing pattern)

### 8. Configuration with Defaults

**Decision**: Optional ~/.csmrc, sensible defaults if missing.

**Rationale**:
- Works out-of-box (no config required)
- Customizable for advanced users
- Defaults cover 90% of use cases

**Trade-off**:
- Pro: User-friendly
- Con: Two code paths (with/without config) - acceptable

**Confidence**: ⭐⭐⭐⭐⭐ (standard CLI tool pattern)

## Risk Analysis: What Could Go Wrong

### Risk 1: Migration Concurrency ✅ MITIGATED

**Original Risk**: Two processes load same v1 manifest, both migrate, race condition.

**Mitigation** (added in S4 v2):
- Acquire lock BEFORE migration
- Check .v1.bak exists (idempotency)
- Test TS-INT-16 verifies concurrent safety

**Residual Risk**: LOW (multiple layers of protection)

### Risk 2: Performance Targets Not Met ⚠️ MEDIUM

**Risk**: Benchmarks don't meet targets (resume < 3s, etc.)

**Mitigation**:
- Batch operations (status, UUID check)
- Streaming (history.jsonl)
- Profiling planned if targets missed

**Residual Risk**: MEDIUM (targets are aggressive but achievable)

**Contingency**: Adjust targets if necessary, document reasoning

### Risk 3: Integration Test Flakiness ⚠️ MEDIUM

**Risk**: Tests intermittently fail in CI

**Mitigation**:
- Test isolation (/tmp/csm-test-XXX per test)
- Mock tmux for CI (no external dependencies)
- Cleanup in t.Cleanup()
- Run 10× to verify stability

**Residual Risk**: MEDIUM (tmux tests inherently racy)

**Contingency**: Skip tmux tests in CI if flaky, run locally

### Risk 4: Scope Creep ✅ PREVENTED

**Risk**: Feature requests during implementation

**Mitigation**:
- All features locked in requirements (D4)
- "Out of Scope" sections in all plans
- Deferred features documented (Phase 4)

**Residual Risk**: LOW (clear scope boundaries)

### Risk 5: Implementation Complexity Higher Than Estimated ⚠️ MEDIUM

**Risk**: 71 hours estimate is too low

**Mitigation**:
- Detailed specs reduce unknowns
- Buffer day in timeline (9 days for 71 hours)
- Can extend if needed (not a hard deadline)

**Residual Risk**: MEDIUM (estimates are estimates)

**Contingency**: Extend timeline, document actual hours for future estimates

## Lessons Learned

### What Worked Exceptionally Well ✅

1. **Multi-persona reviews caught blind spots**
   - Example: Go Dev focused on code, Security noticed permission issues
   - Result: More robust design

2. **Iterative refinement improved quality dramatically**
   - Average +1.46 point improvement from R1 to R2
   - All phases ended at 8.8-9.5/10

3. **Detailed specifications eliminated ambiguity**
   - Implementation will be straightforward (everything specified)
   - No "what should this be?" questions

4. **Planning before coding saved time**
   - 1 day planning vs 6-9 days implementation
   - Design flaws caught in markdown, not code

5. **Wayfinder methodology enforced quality**
   - ≥8.5/10 threshold prevented rushing
   - Stop-and-review at each phase caught issues early

### What Could Be Improved 🔄

1. **Round 1 scores were consistently low (7.7-8.2)**
   - Pattern: First attempt always misses details
   - Improvement: Could create internal checklist before R1 review
   - Impact: Might reach 8.5+ on R1, skip R2

2. **Test fixture creation left to implementation**
   - Specs say "create testdata/" but don't provide actual files
   - Improvement: Could generate sample manifests during planning
   - Impact: Implementation would start faster

3. **Performance targets are estimates**
   - Targets (< 3s resume, etc.) not validated
   - Improvement: Could prototype critical paths to validate
   - Impact: More confidence in feasibility

4. **No explicit risk prioritization**
   - All risks listed, but not ranked
   - Improvement: Could use risk matrix (probability × impact)
   - Impact: Better focus on high-priority risks

### What We'd Do Differently Next Time 🔮

1. **Front-load edge case thinking**
   - QA persona always found missing edge cases in R1
   - Next time: Brainstorm edge cases before creating artifact
   - Expected impact: Higher R1 scores

2. **Create code examples earlier**
   - S4 had 40+ code examples, helped reviewers
   - Next time: Include code examples in all phases (D2, D3)
   - Expected impact: Easier to spot implementation issues

3. **Prototype risky components**
   - Migration concurrency, UUID optimization were high-risk
   - Next time: Write throwaway prototype to validate approach
   - Expected impact: More confidence, fewer surprises

4. **Document decision rationale inline**
   - Rationale was in review feedback, not main docs
   - Next time: Add "Why?" sections in phase documents
   - Expected impact: Easier to understand later
